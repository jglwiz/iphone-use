# 电脑串口控制 iPhone：实测方案与实验记录

本文汇总截至 2026-11-17 的本机实测、手机操作及其证据。主项目是本仓库，`esp32-iphone-agent-windows-ble-hid` 是工作区内保留的参考项目。下面记录双 HID 整合前的历史 USB 和 BLE 实验。当前同板双输出配置见 [串口控制说明](../../cli/doc/serial-control.md)，独立取帧部署见 [Windows 环境说明](../user/windows-setup.md)。

## 实测通信方式

```text
USB 实验：电脑 → USB 转串口 → ESP32-S3 → USB HID → iPhone
BLE 参考：电脑 → USB 转串口 → ESP32-S3 → BLE HID → iPhone
画面观察：iPhone → AirPlay → 电脑上的 UxPlay / 取帧服务
```

两条输入链路中，电脑到 ESP32 都使用串口；区别在 ESP32 到 iPhone 的 HID 传输。上游 Handsy 还有电脑通过 BLE 或 Wi-Fi 向板子发命令的 CLI，以及手机 App 通过 BLE 控板的方式；那些是控制通道，不应与 ESP32 向 iPhone 提供的 BLE HID 混同。此前为了验证上游 CLI，曾将本机与 USB 板的 CLI 控制服务配对，但该配对不是下面 USB 串口实验的前提。按用户决定，上游 CLI/MCP 的本地未提交改动已撤回。

| 项目 | USB HID 实验 | BLE HID 参考 |
| --- | --- | --- |
| 板与固件 | 新 ESP32-S3 板，主项目 `hardware/hid_bridge` 的本地绝对鼠标构建 | 参考项目 `firmware/serial_ble_hid`，实测记录涉及 0.4.1/0.4.2 等版本 |
| 电脑到板 | 独立串口，测试时为 COM24；本机临时诊断桥转发 | 独立串口，参考项目的常驻 Backend 管理会话 |
| 板到手机 | 原生 USB 口的有线 HID | BLE HID，需手机与对应 HID 外设连接 |
| 串口消息 | 文本行，如 `10003 scroll_by 1`；按编号返回结果 | 带版本、会话、请求编号和操作的 JSON 行；需 `hello` 和会话租约 |
| 鼠标报告 | 10：绝对坐标；11：按钮；12：滚轮 | 4：绝对坐标；5：按钮；2：滚轮；BLE value 不包含 Report ID |

两种串口协议不能直接互换。上表中 `10/11/12` 是本地 USB 分离报告布局，BLE 报告编号来自参考固件；它们表达相似的功能，不表示两边连接、配对或校准状态相同。USB 使用的串口桥位于工作区 `.runtime/handsy-usb-test/serial_bridge.py`，通过本机端口 8896 接收测试请求；它是临时工具，不属于本仓库正式 PC 服务。参考项目的画面服务使用 8892，USB 输入没有经过该 BLE Backend 的输入链路。端口号和进程状态均以实际运行环境为准。

## 硬件与首次启动

新板购买型号为 ESP32-S3-WROOM-1；esptool 识别为 ESP32-S3 revision 0.2、16 MB Flash、封装内 8 MB PSRAM 和 40 MHz 晶振。容量与 N16R8 对应，但未核对模组丝印，PCB 厂商和型号未确认。开发板的串口 Type-C 接电脑，原生 USB/OTG Type-C 接 iPhone；本机重插后串口曾编号为 COM24，不能把这个编号作为永久设备身份。

新板首次上电时，原生 USB 反复断连，独立串口持续输出 `invalid header: 0xffffffff` 和看门狗复位。烧录前读取的整片 16 MB Flash 均为 `0xFF`，与没有有效启动镜像的现象一致；这不等于完成了供电或全容量写入测试。原始 Flash 备份保存在工作区 `.backups/handsy-new-board-before-flash-20261116.bin`。

随后构建并刷入主项目的 USB 绝对鼠标固件，配置 16 MB Flash、8 MB OPI PSRAM 和 `ABS_POINTER=1`。第一次 `0 status` 返回 `usb=off`；重新连接手机侧 USB 后为 `usb=ok`。后续滚轮修改的本地开发固件沿用版本字符串 0.2.5；它不等于上游发布的同版本镜像。2026-11-17 烧入的 `scroll_by` 本地构建 SHA-256 为 `285b901746e4446f218563a64ade17b63d928232e84f22326faa6b7015df09c5`，烧录时仅写应用分区并通过写入校验。

## USB 定位、点击与键盘

用户确认辅助触控开启后，在该条件下继续了 USB 点击及滚动对照。`abs X Y` 使用 0–32767 的绝对坐标；在 496×1080 的投屏画面上，30%/30%、70%/65%、中心及四个 10%/90% 位置的指针目测接近目标。实验未证明所有像素和屏幕方向均可达；一次同点重复因指针隐藏没有独立可见证据。USB 不必照搬上游相对鼠标的校准流程，但绝对报告本身也不能证明实际落点准确。

首次对主屏设置图标发送 `click` 后进入编辑状态，表现类似长按；当时没有足够的报告日志判断根因。随后加入内存中的 `HID_TRACE`，在其他页面三次观察到按下和松开约相隔 60 ms、USB 发送调用成功，且页面确实返回；这不能反推首次异常的原因。初期在单个测试控件上的成功也不能证明所有控件均可用。

在 Safari 事件页比较后，本地 USB 固件采用与 BLE 参考方案相近的分离报告：绝对位置、按钮和滚轮各用独立报告。对照中的上游合并布局没有产生完整点击事件；分离布局下三次普通单击和一次 150 ms 按压各使测试按钮计数增加一次。700 ms 按压在网页中产生约 702 ms 的按下到松开，但最终被页面识别为点击，不能作为系统长按菜单通过的证据。另一次输入 `abc123` 后退格，页面得到 `abc12`。发送返回 `ok` 只证明命令处理结果，页面事件或新鲜画面才是本次效果证据。

## 滚动和拖动实验

单条滚轮命令以及通过临时桥约 350 ms 间隔发送的报告均得到回复，Safari 也收到 `wheel` 事件，但页面没有滚动。用户手动确认测试页可以滑动；随后以约 100 ms 间隔连续报告，页面向上从 `scrollY=500` 到 `0`，向下从 `0` 到 `483`，快捷指令列表也发生滚动。随后将这个节奏放入固件。

固件 `scroll_by AMOUNT` 接受整数 -4 至 4：正数向下、负数向上、零不动。它在当前指针所在的滚动区域发送一组报告；量是大致动作单位，不是固定像素。Safari 实测 `1` 从 0 到约 626、`-1` 返回 0；`2` 到约 797 时触底，`-2` 返回 0；`±4` 也分别到达页面底部并返回。零值无滚动，`5`、小数和额外参数被拒绝。由于页面触底，这组实验不能证明位移与数值严格成比例。若串口超时或断连，滚动可能已部分执行，不应自动重放。

测试页上，按住并横向拖动专用物件时，可信事件显示按钮保持按下，物件横坐标约从 39 移到 102 CSS 像素，松开后按钮为 0。但在页面空白处慢速或快速上拖时，虽然收到触摸移动事件，`scrollY` 不变；物件拖动成功不能当作页面拖动滚屏成功。临时换成上游合并报告布局及标准相对 USB 鼠标后，在同一页面上拖动仍未滚屏；合并布局的物件按下/移动也没有得到确认。对照结束后恢复分离报告固件。这些结果只覆盖当前 iPhone 的 Safari 测试页，不能概括所有 iOS 版本或应用。

## BLE 参考链路的实测边界

参考项目曾通过电脑串口、ESP32 BLE HID 和 iPhone 的辅助触控完成点击及绝对定位测试。其 0.4.1 的独立按钮报告有网页事件和原生界面点击证据；0.4.2 的原生绝对定位在竖屏条件下，九点检查及三次复位重连后的有限复测通过，包含同点重复。实测真实四角仍有约 20 px 内缩，不能宣称整个屏幕每个像素都可达；物理旋转与长期稳定性没有因此得到验证。

BLE 的坐标校准和响应检查用于识别当前设备、姿态及实际指针响应；USB 测试中直接映射成功不代表 BLE 自动具备相同校准结果。BLE 历史上出现过方向异常及按键修饰符不稳定，对照中没有唯一确定根因。参考源码和记录位于工作区 `esp32-iphone-agent-windows-ble-hid/` 的 `backend/doc/` 和 `firmware/serial_ble_hid/doc/`；这些证据不随本仓库分发。

## 手机设置与快捷指令

用户确认辅助触控已开启；悬浮菜单中的“轻点一下”不是 USB 鼠标按钮映射，实验没有将其改成“无”。临时开启过全键盘控制做滚动对照，记录显示之后恢复原状态；豆包输入法也恢复了原状态。

串口 USB 点击与滚轮也用于设置定时暂停播放。解锁状态下验证到计划时刻触发暂停，已暂停时运行快捷指令不会恢复播放。设置方法和验证边界见 [定时暂停播放](../user/iphone-pause-playback.md)。
