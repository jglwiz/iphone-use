# 独立取帧的归属与生命周期

旧 BLE 项目的 8892 同时承载控制和截图，主项目虽然已经改用 CLI/MCP 串口输入，仍通过该进程转发截图。这使停用旧项目会连带失去画面。现在只迁移原 `airplay/` 的不可变快照、命名管道解码、接收器发现及 HTTP 服务；旧动作 API、串口 worker、校准与管理器不迁入。

`iphone-use` 自有 Python 环境运行采集器，UxPlay 保持外部程序。命名管道沿用 `hidagent-frames`，这是与现有接收器交换原始视频的约定，不代表依赖旧 Python 项目。496×1080 I420 的宽度须可被4整除，避免 GStreamer 行对齐导致错位；不顺便改变已验证的编码链路。

启动先绑定 HTTP，再独占创建管道，最后才允许接收器启动配置。已有接收器不重启、不覆盖配置。首次启动或重连恢复须明确区分：服务可达、管道连接、有快照、真实手机投屏状态。当前缺少可信手机连接事件，`mirroring_state` 保持 `unknown`；读管道 EOF 清掉旧快照，不能以帧龄推断断连。

图像、时间和 ID 通过同一不可变快照发布。重复读取不更新时间、不分配新 ID；新解码帧才发布。服务允许读取超过五秒的旧快照，CLI 按已有规则返回 observation_only。即便图像内容相同，新收到的真实视频帧仍有自己的 ID/时间；这与给缓存伪造新时间不同。操作后的效果判定由 CLI 的帧门槛及外部页面事件完成，不由 HTTP 200 或 fresh 代替。

服务停止只处理自己的 PID，校验进程创建时间和命令行，防止 PID 重用误杀。接收器不属于采集器生命周期；控制 CLI 更不属于采集器。管道读线程正常退出时取消同步 I/O，由读线程唯一关闭句柄。Windows 外部进程终止由系统释放句柄。

代价是采集器重启可能使接收器的视频输出会话失效。2026-11-18 本机切换旧采集器时，虽然没有显式终止 UxPlay，它仍在管道关闭后自行退出；新服务以 start 模式重新启动接收器，用户重新选择投屏后才能恢复。不能为了掩盖这一点自动杀掉 UxPlay。任何明确的接收器改名/重启需在部署切换中单独记录，不能写成无中断升级。

自动化测试覆盖静止旧帧、快照原子性、清空和恢复、HTTP/管道占用以及附着模式不修改接收器。真实断开、手机恢复与控制效果需要实机证据，不能由这些测试推定。
