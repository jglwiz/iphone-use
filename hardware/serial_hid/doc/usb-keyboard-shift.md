# USB Shift 兼容性调查

`0.3.1-serial`已整合USB键盘接口声明修正，正式构建、刷写校验及本轮USB/BLE键盘和鼠标回归通过。USB原生发送时序、BLE时序、共享动作引擎及CLI/MCP API均保持原样。**间歇性Shift失效的根因尚未定位，不能把本次恢复描述为永久修复。**

## 症状和历史边界

2026-11-18，iPhone 的 English (US) 输入法及正式验收页中，USB 输入 `1a_A-1` 得到 `1a-a-1`；显式 `shift+a`、`shift+-` 和单字符 `A` 同样未产生预期修饰效果。小写、空格和退格正常。开发板重启后，原 `0.3.0-serial` 固件再次复现；一次重启没有解决问题。

历史核查没有找到“最近提交把已验证的 USB Shift 改坏”的证据：

- `60c2e3c` 引入串口双 HID 时，USB 保留 Arduino 原生键盘调用；BLE 单独采用修饰键提前建立和分步释放。
- 更早的 `hid_bridge` 也先构造鼠标、后构造键盘。因此“首个HID对象不是键盘协议”并非测试整理时才引入，不能据此认定新双通路提交造成回归。
- `2913c06` 清理旧组件时，只修改串口固件的共享头文件路径；移动前后动作引擎内容相同。
- `0d37743` 增加正式验收测试，没有修改或刷写键盘固件。
- 早期 USB 日志存在 `Safari`、`Settings` 等命令，但命令成功和搜索到应用不能证明实际大小写正确。旧 USB 网页验收覆盖小写、空格、退格；精确 `1a_A-1` 的成功记录属于 BLE 验收。

这限定了现有证据，不能反过来断言所有历史 USB Shift 输入都失败。CLI 的可打印 ASCII 转换会原样保留 `A` 和 `_`，正式页面关闭自动大写和自动纠正。

实验前完整读回16MiB Flash，核对设备身份及实际app0分区。当前应用前669696字节与此前正式镜像逐字节相同，SHA256均为`739458ed9e7f4d71e944abbc5ef0d825f4a5b55283e13930c81484ad269727cc`。因此不能把本次失败解释为当前设备运行了另一份同版本固件。

## 实验方法

先在原固件、同一页面及英文输入法下对比 USB/BLE。随后使用隔离实验固件，在同一次启动内切换原生 USB、分步报告（修饰键提前量0ms）、分步报告（提前量200ms）。后两者使用相同字符保持及释放间隔。返回原生方式复测，区分时序改变和重启或输入法变化的影响。

判据是可信网页事件中的精确文本和码点，并核对 CLI/MCP 回执、输出通路、报告计数和最终释放。板端回执与实验报告日志只能说明本地提交，不能替代手机效果。只有实验有效后才整合正式代码，再重新构建、刷写和回归。

本机原始证据保留在工作区 `.runtime/usb-shift-fix/`，隔离原型在 `task/serial-control/lab/usb-shift/`；二者不属于正式运行依赖。

## 对照中的新线索

原固件在同一页面的BLE同样丢失Shift。BLE测试期间USB调用数83不变、BLE报告数3→37，最终无按键保持；不是误走USB。此前参考项目也记录过同一BLE时序跨连接失败后恢复的情况，因此200ms提前量不是充分的修复依据。

Arduino ESP32 3.3.12的`USBHID`只在首次构造时保存接口协议。串口固件先创建默认协议NONE的通用发送器，再创建键盘；键盘构造不能覆盖这一选择。隔离对照只把首个对象显式初始化为KEYBOARD，不改变原生键盘时序、HID报告内容或BLE发送逻辑。外部同平台的[第一手复现](https://github.com/adafruit/Adafruit_nRF52_Arduino/issues/870)支持调查此方向，但不替代本机实测。

## 必须保留的反例

首次刷入实验镜像后，仍为NONE接口、未改发送方式的native模式就恢复成功。相同boot下native、staged0、staged200的完整增量均为`1a_A-1A_A`；后续鼠标点击并聚焦新页面后，native仍正确输入`1a_A-1`。因此不能将恢复归因于200ms延迟、分步报告或尚未刷入的KEYBOARD接口变体。

此次刷后首次文本前没有发送定位、点击或滚轮；另一个显著差异是BLE虽已连接加密，但报告订阅由基线7186变为0、未就绪。随后通过USB仅重新配对Handsy，恢复全部订阅；同一boot、同一页面的USB native和BLE各输入`1a_A-1`及`shift+a`，实际增量均为`1a_A-1A`，计数确认分别走各自通路，最终释放。

因此“BLE两路同时就绪”本身也不足以稳定复现失效。刷写、重连和iPhone内部处理仍是未隔离变量，成功恢复不能替代根因证明；目前不将增加延迟整合到USB，也不把KEYBOARD接口候选改动描述为已证实的故障根因修复。

## 接口修正与整合

KEYBOARD接口实验变体通过了USB短串`1a_A-1`、显式`shift+a`/`shift+-`、MCP单字符`A`、24字符混合文本、普通空格与退格。点击使计数0→1，正负滚轮使scrollY 0→626→0，最终held=0。屏幕键盘仍可见，不能据此声称已证明iPhone内部的设备分类发生变化。该次刷后BLE订阅为0，变体的BLE输入未运行。

选择整合的是明确的接口声明：首个通用发送器使用`USBHID(HID_ITF_PROTOCOL_KEYBOARD)`，与随后注册的键盘用途一致，并提供keyboard boot能力。没有整合实验模式、trace、配对脚本或额外延迟；正式运行不依赖实验目录。原USB固件`hid_bridge`保持历史状态，本次修正只针对当前维护的串口双HID固件。

正式固件版本标为`0.3.1-serial`，以便区分实验与已部署版本。发送成功仍不等于手机效果验证。若再次丢Shift，应先保留两路ready、boot/连接代次、实际输入法和可信事件，再用相同短串对照；不要自动重放业务输入，也不要通过反复刷写掩盖复发条件。

## 正式版实机回归

正式bin为669696字节，SHA256 `1c8cfd3a0412687147cb5c8fa128dd3868b48d51fbde41f70249e034594d840c`；仅写本板app0，独立`verify_flash`通过。实际版本`0.3.1-serial`，boot为`eb3e195663c101d0`。沿用正式CLI/MCP，通过原AirPlay观察，未重启投屏服务。

| 用例 | USB | BLE |
|---|---|---|
| CLI `1a_A-1`、`shift+a`、`shift+-`及MCP `A` | 精确插入`1a_A-1A_A` | 精确插入`1a_A-1A_A` |
| MCP 24字符混合文本 | 完整`A_a-1!A_a-1!A_a-1!A_a-1!` | 同样完整，覆盖超过16字节的分块 |
| 普通空格和退格 | U+0020；连续两次退格分别移除空格和末尾`!` | U+0020；退格恢复输入前文本 |

| 正负滚轮 | scrollY 0→631→5 | scrollY 0→650→24 |

主代理独立审查可信输入事件、插入前后完整文本、码点及状态计数；没有仅凭字符串包含旧测试内容判断通过。正式键盘两路的页面为`c5e17a48476a403cbf21d5a25eb3f875`，USB短组ack285→322、长组322→418；BLE短组490→527、长组527→623。BLE鼠标准备时页面重新加载为`07f7a883d4794ec3a15aa2ef1b446997`，该阶段按新页面独立验收，不宣称与键盘是同页面连续窗口。共用run为`60d180855c46421bb9a42e71eb624484`，事件在`baseline/run/events.jsonl`，各正式命令和快照使用`baseline/formal-*`前缀。

本轮刷写后多次遇到BLE已连接加密、但订阅为0。仅重新配对Handsy后恢复7186及ready；这项自动恢复问题没有在本轮修复。最终正式配对由实验辅助脚本匹配包含目标名称的新鲜弹窗帧后单次确认，证据位于`formal-pair/`，不属于正式控制API。

本次未验证长期运行、跨设备/系统兼容、物理拔线及全部旧测试迁移矩阵。旧PC通信测试及专用辅助代码仍保留；键盘本轮通过不自动满足全部清理条件。没有改动CLI源码，因此未重复执行无关Go/Host C测试。
